# 飞线与地图背景图 —— 需求确认说明书

> 用途：拿到「要做飞线 + 地图背景图」这类需求后，用它把产品嘴里的**感觉**变成你能写进代码的**参数**，并在动手前把返工风险摁死。
>
> 适用对象：三维/大屏地图类需求（three.js、echarts GL、deck.gl、Cesium 均可套用）。

---

## 一、先判断这活能不能直接开干（3 分钟分级）

产品说「加个飞线」「背景图换个高级的」，先别急着答应，先判断落在哪一级：

| 级别          | 典型说法                                                     | 影响面                 | 处理方式                                       |
| ------------- | ------------------------------------------------------------ | ---------------------- | ---------------------------------------------- |
| **L1 调参级** | 「线再亮一点」「颜色再蓝一点」「流动快一点」                 | 只改数字，不动结构     | **不开会**。四宫格对照图发过去让他圈，圈完就干 |
| **L2 结构级** | 「要有拖尾」「要能点击看详情」「要两套背景能切」             | 加交互、加状态、加组件 | 30 分钟对齐，出选项表                          |
| **L3 架构级** | 「背景要跟着地图转」「要能放大看具体机房」「大屏和手机都要」 | 换实现方式，改架构     | **必须先确认**，返工代价最高                   |

**一句话原则**：先用一句话判定级别，别用 L1 的态度去接 L3 的活。绝大多数翻车都是把 L3 当 L1 接了。

---

## 二、确认的标准动作（5 步，别跳）

1. **要参照物。**
   信息量排序：一句描述 < 一张截图 < 一段录屏 < 一个能上手拖的原型。
   「我要那种高级点的」= 0 信息量。追一句「有没有见过类似的？截图给我」能省两天。

2. **拆成选项，并且标上代价。**
   每个点给 2～3 个选项，每个选项后面写清「多花多久 / 性能差多少 / 以后好不好改」。
   产品只有在**有代价的选择**里才会给真答案；给他开放题，他只会说「都要」。

3. **出对照图，让他圈。**
   同一个机位、同一份数据，四宫格不同参数。指着图说「A 还是 B」。
   不要用文字描述共识 —— 「有科技感」这四个字，你和他的理解一定不一样。

4. **反向确认边界。**
   「这样不行吧？」比「这样可以吧？」有效得多。
   把最难看的、最卡的、最不合理的那个版本也做出来给他看，让他亲口否掉。

5. **落成一句可测量的验收条款。**
   写进需求单，写不进验收标准的「效果」，等于没确认。

## 三、飞线：必须问清的 7 件事

| #   | 问什么             | 产品可能怎么答               | 你要落到的参数                                    | 不问会怎样                                       |
| --- | ------------------ | ---------------------------- | ------------------------------------------------- | ------------------------------------------------ |
| 1   | **两端到底是什么** | 「城市之间」「机房到用户」   | 坐标精度：省中心点 / 市中心点 / 具体点位          | 后期接真实经纬度，发现和底图比例对不上，整层重做 |
| 2   | **一共多少条**     | 「就几条」「看数据」         | 10 / 100 / 1000+ 三档                             | 100 条逐条绘制很流畅，3000 条直接掉到 8 帧       |
| 3   | **形态**           | 「弯的、带个亮点」           | 弧线高度、拖尾长度、头部光点大小、是否落到地面    | 做出来是「抛物线」他想要「贴地弧」，全程返工     |
| 4   | **动效节奏**       | 「一直在流动」               | 单向/双向、一圈几秒、是否无缝循环、进出场有无渐显 | 频率不对，大屏看 10 分钟就晃眼                   |
| 5   | **颜色有语义吗**   | 「好看就行」or「按告警变色」 | 单色装饰 / 按流量定粗细 / 按状态变色              | 做成装饰性配色，后面要加告警红，整套色板推翻     |
| 6   | **要交互吗**       | 「能点一下最好」             | hover 高亮、点击下钻、tooltip 内容字段            | 点击下钻是 L3，做完了才说要，等于重做交互层      |
| 7   | **缩放边界**       | 「能放大缩小吧？」           | 见 3.1，这条最常漏                                | 验收时被拖远了看，线断了，说不清是 bug 还是设计  |

### 3.1 为什么「缩放到什么级别」必须单独问

这条几乎每次都被漏掉，但它是大屏项目里最典型的「验收翻车点」。

**飞线不是一条真正的线。** 它是一条**始终正对镜头的三角带**（ribbon），宽度写在**世界坐标**里 —— 比如 0.66 个地图单位。
镜头拉近时，0.66 世界单位在屏幕上占十几个像素，看起来饱满顺滑；
镜头一拉远，它投影到屏幕上只剩 **0.7 个像素**，不到一个像素宽的线，显卡只能「这一帧画、下一帧跳过」，于是看起来一截一截、断断续续。

**这不是 bug，是「线宽用世界单位」的必然结果。** 你跟产品解释时就这么说：

> 「线宽是按地图尺度定的，镜头拉远了，它在屏幕上就细到画不出来了。要好看，得给线宽加一个『最小屏幕像素』的下限。」

所以必须问三个数：

| 问题                                                        | 答案影响                                              |
| ----------------------------------------------------------- | ----------------------------------------------------- |
| **最终投屏分辨率是多少？**（1920 / 2560 / 3840 / LED 拼接） | 决定线宽、字号、面板尺寸的基准                        |
| **观众大概离屏幕多远？**                                    | 远了要整体加粗、提高对比度；近了要压细、减少信息密度  |
| **现场会不会有人缩放 / 转视角？**                           | 会 → 必须做像素下限；不会 → 可以锁死 zoom，省一堆适配 |

拿到答案后落到处理策略：

| 场景                   | 处理                                                         |
| ---------------------- | ------------------------------------------------------------ |
| 只在固定机位 100% 下看 | 默认参数即可，锁死缩放最省事                                 |
| 允许缩放、拖拽         | **必须做屏幕像素下限**：拖尾 ≥ 2px、轨道 ≥ 1.2px、光点 ≥ 6px |
| LED 大屏远距离观看     | 整体线宽 ×1.5，降低颜色饱和度（远看高饱和会糊成一片）        |

## 四、地图背景图：先问一句决定架构的话

动手前只问这一句，能省掉一半返工：

> **「这张图，你希望它跟着地图一起转（有透视、会动），还是永远钉在屏幕上不动（像壁纸）？」**

这一句直接分成两套完全不同的实现：

| 他的回答              | 实现方式                              | 技术本质                                   |
| --------------------- | ------------------------------------- | ------------------------------------------ |
| 钉住不动 / 像壁纸     | CSS `background-image`                | **屏幕坐标**，镜头怎么转它都不动，性能最好 |
| 跟着地图转 / 有立体感 | 放进 three.js 场景的一块平面（Plane） | **世界坐标**，有近大远小，会随镜头透视变形 |

> **实战提示**：真实项目往往是**两个都要**。
> CSS 那张负责远景氛围和整体色调（不跟随，永远铺满窗口）；场景里那张负责地面质感和透视（跟随，提供纵深）。
> 只做一个也能跑，但要么「平得像 PPT」，要么「一转视角背景就穿帮」。当前这个页面用的就是双层叠加。

定完架构，再确认这 6 件事：

| #   | 问什么                           | 注意点                                                                                                |
| --- | -------------------------------- | ----------------------------------------------------------------------------------------------------- |
| 1   | **它是「图」还是「氛围」**       | 实景卫星/航拍图（**必须同时问来源和商用授权**）、抽象纹理（可程序生成）、纯渐变加星点（成本最低）     |
| 2   | **要不要多套、谁来切**           | 固定一套 / 给个开关让用户切 / 按主题自动切。切换要不要过渡动画                                        |
| 3   | **主次关系：底图是主角还是配角** | 这是最容易吵起来的一条。配角就必须压暗降饱和，否则飞线在花纹上看不清                                  |
| 4   | **明暗两套主题都要吗**           | 同一张图在暗底上要发光、在亮底上要压色，**不是调个透明度就完事**。只做一套 = 亮色会议室里投出一片灰白 |
| 5   | **投屏形态**                     | 16:9 单屏 / 21:9 超宽 / 竖屏 / LED 拼接。决定图片尺寸和**裁切锚点**（按中心裁切会把地图主体顶出画面） |
| 6   | **授权和体积**                   | 商用授权有没有？单张压到 ≤ 300KB（WebP），否则首屏等图等到白屏                                        |

给产品的一句话，可以直接抄：

> 「背景图不是越花越好。背景越抢眼，飞线越看不清。要么**背景当主角、飞线少而精**，要么**背景退到后面、飞线当主角** —— 两个都当主角，两个都不好看。」

## 五、方案对照表（拿去让产品选）

| 维度     | 纯 CSS 底图                | three.js 场景底板        | 两者叠加（推荐）     |
| -------- | -------------------------- | ------------------------ | -------------------- |
| 跟随镜头 | 不跟随                     | 跟随，有透视             | 前者不跟、后者跟     |
| 观感     | 平，像 PPT 背景            | 深，有空间感和纵深       | 兼顾氛围与纵深       |
| 性能     | 最省（一张图）             | 多一个 mesh + 纹理采样   | 多一次采样，可接受   |
| 换图成本 | 改一个 CSS 变量            | 要重建纹理、调尺寸       | 两层分开改，互不影响 |
| 主题适配 | 换图 / 加滤镜即可          | 要分别处理混合模式       | 分别处理             |
| 适合场景 | 汇报大屏、以截图和录像为主 | 强调沉浸感、会转视角演示 | 对外演示的主视觉大屏 |

## 七、验收标准怎么写

| 反面写法（永远验收不过） | 正面写法（可测量、可判输赢）                                     |
| ------------------------ | ---------------------------------------------------------------- |
| 飞线要有科技感           | 1920×1080 下，飞线拖尾屏幕宽度 ≥ 2px；缩放到 60% 时连续不断线    |
| 背景图要高级             | 4 套预设可切换，切换无白闪；2560×1080 下地图主体完整可见、无拉伸 |
| 动画要流畅               | 100 条飞线同时运行时，Chrome 下稳定 ≥ 50 FPS（i5 集显）          |
| 暗色亮色都要好看         | 亮色主题下背景不出现发灰白块，飞线与背景对比度 ≥ 3:1             |
| 性能要好                 | 首屏 3 秒内出现地图，背景图单张 ≤ 300KB                          |

**判断标准**：写出来的这句话，换个人来验收，结论应该和你一样。做不到，就是还没确认完。

## 八、15 分钟会议脚本（照着念）

1. 「这版是给谁看的？**汇报演示**还是**日常值班盯着看**？」（决定信息密度，演示要炫，值班要稳）
2. 「投在什么屏上？**多少分辨率、观众离多远**？」（决定线宽、字号）
3. 「现场会不会有人上去**拖拽、缩放**地图？」（决定要不要做像素下限）
4. 「飞线**几条**？数据是死的还是实时接？」（决定技术方案）
5. 「线的**颜色有含义吗**？还是纯装饰？」（决定色板要不要可配置）
6. 「背景图，你希望它**跟着地图转**，还是**钉在屏幕上**当壁纸？」（决定架构）
7. 「背景和飞线，哪个是**主角**？」（决定视觉权重）
8. 「有没有**见过类似的**？给我一张截图或者链接。」（最重要的一问，放最后压轴）

## 九、常见翻车点清单

- 把「高级感 / 科技感 / 炫一点」当验收标准 → 永远验收不过，改到项目结束
- 只看了设计稿截图，没代入真实数据量 → 100 条很酷，3000 条成了毛线团
- 没问投屏环境 → 现场投影仪偏色，蓝色飞线投出来发黑
- 背景图来源不明 → 上线前被要求换掉，白干
- 只做了暗色主题 → 客户会议室是亮色，投出来一片灰白
- 验收时才提「顺便导出一段视频」→ 帧率不够，补录一整天
- 只在一个分辨率下验收 → 换到 3840 宽屏，面板全挤在一起

## 十、飞线观感问题速查（大白话版）

> 本章不写具体数值，所有参数都当「旋钮」看：只记往大拧、往小拧各会变成什么样。
> 前面章节讲"确认需求"，这一章讲"上线后画面不对，先拧哪儿"。

### 10.1 一句话心智模型

**保底线管「断不断」，拖尾管「好不好看」，条数和泛光管「卡不卡」。**

> 注意：**台阶锯齿不归保底线管**。保底只解决「线细到消失」，解决不了「斜边成楼梯」——后者要开柔化。

### 10.2 先对号入座：看到什么现象，先拧哪个旋钮

| 你看到的现象                               | 先拧这个                             | 再考虑                       |
| ------------------------------------------ | ------------------------------------ | ---------------------------- |
| 拉远后线整段消失、一闪一闪                 | 最细保底 ↑                           | 尾部变暗速度 ↓、泛光门槛 ↓   |
| 飞行时只有尾巴断、头部是连续的             | 最细保底 ↑（必须作用在「收细之后」） | 尾部变暗速度 ↓、拖尾亮度 ↑   |
| 斜边呈台阶状、缩小地图时更明显、放大就平滑 | 开后处理多重采样                     | 保底加封顶、点数按屏幕自适应 |
| 某个视角突然掐断，转个角度就恢复           | 左右方向退化时沿用上一个采样点方向   | —                            |
| 断的位置一直在变，像踩格子                 | 限制单帧最大时间步长                 | 减少条数、降低像素密度上限   |
| 整体糊成一团、看不清细节                   | 拖尾长度 ↓、泛光强度 ↓               | 减少条数                     |
| 线太抢眼、压住了地图                       | 头部亮度 ↓、泛光强度 ↓               | 轨道与拖尾的宽度比 ↓         |
| 画面卡顿、掉帧                             | 条数 ↓、像素密度上限 ↓               | 泛光强度 ↓、采样点数 ↓       |
| 亮色主题下飞线几乎看不见                   | 改用普通混合（不要加法混合）         | 提高拖尾亮度                 |
| 流星像节拍器，一颗接一颗很机械             | 停顿 ↑、速度个体差异 ↑               | —                            |
| 弧线全一样高，像拱门                       | 弧高随机抖动 ↑                       | 弧高基础值 ↓                 |

### 10.3 旋钮对照表

| 旋钮（代码参数）                                                 | 它管什么                         | 往大拧                             | 往小拧                                | 好比                               |
| ---------------------------------------------------------------- | -------------------------------- | ---------------------------------- | ------------------------------------- | ---------------------------------- |
| **最细保底**（`MIN_STREAK_PX` / `MIN_TRACK_PX` / `MIN_HEAD_PX`） | 相机拉远时，线最细能细到什么程度 | 远处也看得清，不容易断             | 拉远就断成一截一截                    | 给线画一条「最细不能细过它」的底线 |
| **拖尾长度**（`fly.streakBand`）                                 | 流星屁股后面拖多长               | 长，像飘带，容易糊成一片           | 短，干脆利落，但可能像只萤火虫        | 彗星的尾巴                         |
| **尾部变暗速度**（拖尾衰减指数）                                 | 尾巴从亮到暗有多快               | 暗得慢，整条尾巴都看得见（且显粗） | 暗得快，尾巴迅速消失 → 看着就「断」了 | 手电筒关灯的快慢                   |
| **白热核长度**（`CORE_SPAN`）                                    | 头前面那截纯白的长度             | 白色部分长，像根白棒子             | 只剩一个小亮点                        | 火柴头的大小                       |
| **头光点大小**（`fly.headSize`）                                 | 头部那颗发光球的直径             | 球大、抢眼，但会盖住线             | 球小，几乎看不见                      | 流星的头                           |
| **头光点亮度**（`fly.headOpacity`）                              | 那颗球的亮度                     | 亮，泛光强                         | 暗，像蒙了灰                          | 灯泡的瓦数                         |
| **弧高**（`fly.arcBase` / `arcMax` / `arcRatio`）                | 线拱起来多高                     | 高，像喷泉、像天桥                 | 低，像贴地爬                          | 桥拱的高度                         |
| **弧高抖动**（`arcJitter`）                                      | 每条线的弧高差异                 | 高低错落，自然                     | 全部一样高，像拱门                    | 一排树高矮不齐                     |
| **速度**（`fly.speed`）                                          | 飞完全程要多快                   | 快，热闹但容易眼花                 | 慢，优雅但显得懒                      | 流星划过的速度                     |
| **停顿**（`fly.restGap`）                                        | 飞到终点后歇多久再出发           | 歇得久，节奏感强                   | 几乎不歇，像流水线一颗接一颗          | 红绿灯的等待时间                   |
| **条数**（端点数量，见 `useFlyLines`）                           | 同时有几条在飞                   | 多，壮观但容易一团毛线             | 少，清爽但不够热闹                    | 放烟花的数量                       |
| **泛光门槛**（Bloom `threshold`）                                | 多亮才配发光                     | 只有特别亮的才发光，画面干净       | 暗的也发光，整体容易糊                | 筛子：孔小只留大块的               |
| **泛光强度**（Bloom `strength`）                                 | 发光有多晕                       | 晕得厉害，像雾里看灯               | 几乎没有光晕，变成硬线条              | 雾的大小                           |
| **采样点数**（`SEGMENTS`）                                       | 曲线用多少个点连起来             | 弧线更顺滑，但更吃性能             | 弧线有棱角，省性能                    | 用几段折线画一个圆                 |
| **像素密度上限**（`setPixelRatio` 上限）                         | 高分屏上允许多细密地渲染         | 更清晰，但更容易卡                 | 更流畅，但画面发虚                    | 电视的清晰度档位                   |

### 10.4 先分清：「断线」和「台阶」是两回事

这两种现象都会被描述成"一截一截"，但根因正好相反：

| 你看到的                                 | 本质                         | 该动哪                  |
| ---------------------------------------- | ---------------------------- | ----------------------- |
| 线整段消失、一闪一闪、飞着飞着没了       | 线比瓷砖还窄，格子上覆盖不到 | 加最细保底              |
| 斜边是楼梯状，缩小地图更明显，放大就平滑 | 折点被挤在一起 + 边缘没柔化  | 开多重采样 + 点数自适应 |

**最常见的返工就是把台阶当断线去加粗**——线会变粗，台阶反而更明显。

### 10.5 真断线：为什么飞行时更明显

不是动画断了，是那一段**又细又暗**，被显卡和泛光一起吃掉了：

1. **带子比像素格还窄。** 飞线是一条有宽度的带子，镜头一远，投影到屏幕上可能还不到一格的宽度。显卡按「格子中心有没有落在里面」决定画不画，于是有的格子亮、有的格子空。
2. **拖尾是渐变的。** 它从头到尾逐渐变暗，加法混合下越暗就越接近透明。
3. **泛光有亮度门槛。** 低于门槛的部分连光晕都没有，只剩下那点细线，更容易被漏画。
4. **结果**：亮头连续、尾巴一截一截闪 —— 这不是两条曲线拼接，而是同一条线在屏幕上「时有时无」。

### 10.6 台阶锯齿：为什么缩小地图更明显

飞线不是数学上光滑的曲线，它是**用有限个点连起来的折线带**，点与点之间是直线段。

三个原因叠加：

1. **点被挤在一起。** 放大时这些点在屏幕上铺得开，拐角看不出来；一缩小，整条线在屏幕上变短，所有拐点挤进几十个像素里，每个拐点就是一个台阶。
2. **线宽没跟着变细。** 最细保底让线在缩小时保持原来的粗细。线短了、粗了，台阶的「踏步」就显得更夸张。
3. **边缘是硬的。** 后处理通道默认没开多重采样（不让瓷砖涂半色），台阶没有过渡，全是直角。

三个动作，按性价比排：

| 优先级 | 动作                                         | 效果                                 | 代价                       |
| ------ | -------------------------------------------- | ------------------------------------ | -------------------------- |
| 1      | **开后处理多重采样**                         | 边缘按覆盖率涂半色，台阶立刻变柔     | 性能，通常 4 倍采样够用    |
| 2      | **给最细保底加个封顶**                       | 缩小时不再变成「短粗线」，台阶不显眼 | 几乎没有                   |
| 3      | **点数按屏幕自适应**（缩小少画点、放大补点） | 任何缩放级别都顺滑                   | 要改几何重建逻辑，成本最高 |

### 10.7 怎么快速分辨

| 你看到的                             | 大概率原因                         |
| ------------------------------------ | ---------------------------------- |
| 远处断、拉近就好；尾部比头部断得厉害 | 线宽不足 + 泛光门槛                |
| 斜边是楼梯、缩小更明显、放大就平滑   | 折点被挤压 + 边缘没柔化            |
| 只有某个视角断，转一下角度就恢复     | 左右方向在正对镜头时退化翻转       |
| 断的位置一直在变，像踩格子           | 帧率不稳，进度在跳                 |
| 任何距离都断，但远处更明显           | 像素保底没生效（视口尺寸没传进去） |

### 10.8 速记

1. **整段消失** → 最细保底 ↑。
2. **台阶锯齿** → 开多重采样、保底加封顶、点数自适应。
3. **糊** → 拖尾长度 ↓、泛光强度 ↓。
4. **卡** → 条数 ↓、像素密度上限 ↓。

**判断标准**：调参只动旋钮，不改结构；拧完这几组还有问题，才回头查代码实现（采样方式、朝向计算、时间推进）。
