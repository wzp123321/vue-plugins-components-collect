# BI 数据录入台 —— 选型指南

> 接到「做个表格录入页」的需求时，先按业务特征在这里定位：选哪套插件、哪部分必须自己写。  
> 三套实现并列维护：vxe-table、@visactor/vtable、Univer。功能面按同一份需求清单对齐，没有主次之分。  
> 功能状态以**代码**为准，不以官网宣传或早期文档为准。怎么实现、坑在哪，见 `BI数据录入台-实现细节.md`。

## 一、结论

**三套是并列的，不是主备关系。** 新需求进来时三套都要加，能力面按同一份清单对齐；某套架构上做不到的，在第四章标 `✕`，并在需求评审时提出，不靠"降级为技术验证页"绕过。

选哪套由**业务特征**决定，不预设默认值：

| 业务特征 | 选 | 原因 |
| --- | --- | --- |
| 列结构随业务变、要嵌业务组件、要能 e2e 断言 | vxe | DOM 结构，改列只改数组 |
| 十万行级、以看为主、单元格样式驱动 | VTable | Canvas 最省内存 |
| 要公式、多 sheet、导入导出保真 | Univer | 唯一有完整表格语义 |

三套的自研占比相当（vxe 75%、VTable 74%、Univer 46%）——工程量 70% 以上不在渲染层，而在校验、列模型、查询、IO、撤销、模板。所以**换插件不等于换工作量**，选型只看业务特征和你愿不愿意付某个库的改造成本。

落地四条：

1. 新录入台从三套里挑最贴合业务特征的一套复制，列定义、校验、IO、撤销骨架三套等价，可直接搬。
2. **同一需求三套同步加**，否则选型表里的 `✕`/`◇` 会随时间失真，选型就失去依据。
3. 三套外观由 `src/assets/style/bi-entry.less` 统一提供（色板 `--bi-*` + 骨架类 `.bi-*`），新页面挂类即可，不要另写一份。
4. 任何一套做不到的（第四章 `✕`），在需求评审时当场提出，不要等实现时才发现。

## 二、范围与规则口径

| 项   | 口径                                            |
| --- | --------------------------------------------- |
| 列类型 | **仅 4 种：文本 / 数字 / 下拉 / 日期**。布尔、附件、公式列、富文本列均不做 |
| 分页  | **不做**，大表一律虚拟滚动（已实现的分页视图仅作代码参考，不排期）           |
| 协作  | 不做实时协同、评论、@提醒                                 |
| 端   | 仅桌面浏览器，不做移动端适配                                |

四类字段的标准规则（写新页面照此实现）：

| 类型     | 格式                   | 范围                   | 其他          |
| ------ | -------------------- | -------------------- | ----------- |
| **文本** | 正则 `pattern` + 自定义文案 | 长度 `minLen ~ maxLen` | 整列唯一        |
| **数字** | 必须是数值                | 闭区间 `min ~ max`      | 整数、整列唯一     |
| **下拉** | 必须是选项之一              | —                    | 选项不可自由输入    |
| **日期** | `YYYY-MM-DD` 且必须真实存在 | 仅跨列比较                | 显示格式可配，存储恒定 |

- 四种类型都支持**必填**；空值只判必填，不跑其他规则。
- **跨列规则**四种：`≥` / `≤` / `=` / `参照列非空时必填`。文本与日期按字符串比（ISO 字典序即时间序），数字按数值比。
- **唯一性**只比非空值，空值不参与。
- **存储与显示分离**：日期存 `YYYY-MM-DD`，`dateFormat` 只影响单元格与编辑框呈现。

三套与口径的差异（只列不一致的）：

| 规则          | vxe                | VTable              | Univer                  | 处理                      |
| ----------- | ------------------ | ------------------- | ----------------------- | ----------------------- |
| 数字：整数       | ❌                  | ✅ `rules.integer`   | ❌                       | 只有 VTable 有，另两套加一条规则即可  |
| 数字：精度 / 千分位 | ❌                  | ❌                   | ❌                       | 三套都无，接后端时补              |
| 日期：真实日期     | ✅ `isRealDate`     | ✅                   | ⚠️ 仅正则，`2026-02-30` 会通过 | Univer 有真实脏值风险          |
| 日期：显示格式     | ✅ 5 档 + 自定义        | ✅ 3 档               | ❌                       | Univer 只能 `YYYY-MM-DD`  |
| 日期：日历弹层     | ✅ `el-date-picker` | ✅ `DateInputEditor` | ❌ 纯输入                   | Univer 录入体验最差           |
| 日期：范围（起止之间） | ❌                  | ❌                   | ❌                       | 用跨列规则近似                 |
| 校验拦截时机      | 先落值再标红             | **数字列拒写回滚**         | 先落值再标红                  | 要求「绝不留下非法值」只有 VTable 现成 |
| 错误提示        | 标红，无悬停文案           | 同                   | 同                       | 三套都要自己补                 |

## 三、需求 → 选型速查

拿业务那句话，找到最像的一行，看「选谁」和「为什么」。

### 3.1 按数据量

| 业务这么说       | 选               | 说明                                 |
| ----------- | --------------- | ---------------------------------- |
| 「几千条，随手改」   | 三套都行，默认 **vxe** | 这个量级性能不构成差异，比的是改起来贵不贵              |
| 「十万条，还要能编辑」 | **vxe**         | DOM 下 10 万行已实测可用；VTable 也能跑，但编辑弱一档 |
| 「百万行，主要看」   | **VTable**      | Canvas 是它的主场；但单元格不能放业务组件           |
| 「首屏必须 1 秒内」 | **VTable**      | 首次渲染量最小；vxe 十万行要配合虚拟滚动预热           |

### 3.2 按列结构

| 业务这么说             | 选                | 说明                                                   |
| ----------------- | ---------------- | ---------------------------------------------------- |
| 「列是固定的，写死就行」      | **Univer** 最省代码  | 列固定时它 46% 自研占比的优势最大                                  |
| 「业务方要自己加字段」       | **vxe**          | 改 `defs` 数组即重渲染；Univer 每次要整轮重下发                      |
| 「要两层表头」           | **vxe / VTable** | vxe 走 `group`、VTable 走 `groupColumns`；**Univer 做不到** |
| 「列要能拖宽、能冻结前两列」    | **vxe / VTable** | Univer 冻结列只支持首列，改 `xSplit` 且每次重建重算                   |
| 「列要能隐藏 / 排序 / 分组」 | 三套都有             | 差异见第二章                                               |

### 3.3 按编辑体验

| 业务这么说                  | 选                | 说明                                                   |
| ---------------------- | ---------------- | ---------------------------------------------------- |
| 「要和后台其他表单长得一样」         | **vxe**          | 表头与单元格是真实 DOM，Element Plus 组件直接塞进去                   |
| 「要像 Excel：填充柄、复制框、键盘流」 | **vxe / VTable** | 两套都实现了；VTable 的填充柄与键盘流是内置开关，vxe 是自研                  |
| 「单元格里要放按钮 / 标签 / 进度条」  | **vxe**          | `slot` 或 `cellRender`；**VTable 放不进去**，Univer 只能改底色字色 |
| 「单元格要能换行、富文本」          | **Univer**       | 原生多行；vxe 与 VTable 的文本列是单行                            |
| 「要公式、多 sheet」          | **Univer**       | 另两套没有公式引擎                                            |
| 「要撤销重做」                | 三套都有             | 都是自研，vxe / VTable 含列结构快照，Univer 靠命令栈                 |

### 3.4 按校验

| 业务这么说              | 选                  | 说明                                            |
| ------------------ | ------------------ | --------------------------------------------- |
| 「必填、范围、长度、正则、不能重复」 | 三套都能               | 引擎都是自研，规则能力对齐，见第二章                            |
| 「填错不能存进去」          | **VTable**（数字列已实现） | vxe / Univer 先落值再标红，要拦需自己改                    |
| 「鼠标悬停要看到为什么红」      | **vxe** 成本最低       | DOM 加 `title` / `el-tooltip` 半天；Canvas 只能自绘气泡 |
| 「要和后端规则合并校验」       | **vxe / VTable**   | 两套都留了服务端校验入口，Univer 没有                        |

### 3.5 按导入导出

| 业务这么说                  | 选            | 说明                         |
| ---------------------- | ------------ | -------------------------- |
| 「导入导出 Excel」           | 三套都要自研       | 都走 `exceljs` / `xlsx`，能力等价 |
| 「导入要保留原表样式、公式」         | **Univer**   | 只有它认单元格样式与公式（Pro）          |
| 「只要 CSV / 能从 Excel 粘贴」 | 三套都能         | 都支持 TSV 剪贴板互通              |
| 「导入前要给预览、要能选列映射」       | **vxe** 成本最低 | 三套都没做，DOM 版做预览最直接          |

### 3.6 按外观与集成

| 业务这么说             | 选                | 说明                                                     |
| ----------------- | ---------------- | ------------------------------------------------------ |
| 「要跟站点主题/暗色模式完全一致」 | **vxe**          | DOM 直接吃 CSS 变量；VTable 要读计算样式转 `TableTheme`；Univer 精度最差 |
| 「要嵌进现有后台布局」       | **vxe / VTable** | Univer 是整块电子表格，工具条和画布自成体系                              |
| 「表格要撑满容器、不留白」     | **vxe**          | VTable 在隐藏 tab 里初始化会拿 0 宽，必须可见后 `resize()` 重建          |

### 3.7 按可测试与可维护

| 业务这么说           | 选          | 说明                           |
| --------------- | ---------- | ---------------------------- |
| 「要 e2e 断言单元格文字」 | **vxe**    | DOM 可查；Canvas 两套断言不到文字       |
| 「团队没写过 Canvas」  | **vxe**    | 定制全靠 DOM/CSS，学习成本最低          |
| 「需求预计会持续改两年」    | **vxe**    | 列结构、单元格渲染、编辑器都能替换，不锁死        |
| 「一个月内要上线、之后不太动」 | **Univer** | 原生能力最多，起步最快                  |
| 「要能无障碍访问」       | 三套都不行      | Canvas 无语义；vxe 至少能自己补 `aria` |

## 四、插件真正给了什么

一句话：**标 `○` 的全是插件没给、我们自己写出来的代码 —— 不代表插件做不到。**

| 记号 | 含义                       | 怎么读             |
| -- | ------------------------ | --------------- |
| ⬤  | 插件原生，写配置就有               | 白拿              |
| ◐  | 插件给壳（渲染 / 事件 / 命令），逻辑我们写 | 已实现，逻辑在自己手里     |
| ○  | 插件完全没有，我们自研实现            | **能做，而且已经做出来了** |
| ◇  | 插件没有，可自研，本实现尚未做          | 能做，报个工时即可       |
| ✕  | 插件架构上做不到                 | 选型红线            |

> 统计的是**能力条数**；代码行数口径见第五章「自研占比」。

### 4.6 记号统计

|            | vxe   | VTable | Univer |
| ---------- | ----- | ------ | ------ |
| ⬤ 原生       | 10    | 10     | 18     |
| ◐ 半自研（已实现） | 6     | 5      | 7      |
| ○ 全自研（已实现） | 21    | 20     | 6      |
| ◇ 可自研、未做   | 9     | 8      | 11     |
| **✕ 做不到**  | **1** | **4**  | **5**  |

- **`✕` 决定能不能用**：vxe 只有「导出保样式」一项不可能；VTable 多「内嵌组件、e2e、无障碍」；Univer 再多「多级表头」。
- **`◇` 决定报多少工时**；**`○` 决定出问题能不能自己改** —— 这些 `○` 都是仓库里已写好的代码，不是缺失项。
- 典型误读：vxe 的填充柄、复制粘贴、蚂蚁线、键盘流都是 `○`（`useFillHandle` / `useGridKeys` / `useCopyMarquee`），**已经能用**，只是代码归我们。反过来 Univer 的 `⬤` 更多，但换过去等于把已有的 `○` 全部重写一遍。
