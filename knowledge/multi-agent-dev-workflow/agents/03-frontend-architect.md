# 03 前端架构师（Frontend Architect）

产出前端契约诉求与前端设计。设计必须与后端在**契约**上对齐后才能定稿。

## 输入
- `requirement-spec.md`（冻结版）
- `interface-contract.md`（Phase 2 产出共识版，Phase 3 读取）

## 输出
- Phase 2：`契约诉求`——我需要后端给我什么（接口清单 + 字段 + 错误码 + 性能要求）
- Phase 3：`frontend-design.md`（模板见 [`../templates/frontend-design.md`](../templates/frontend-design.md)）

## 上下文预算
- `requirement-spec.md` 全量
- `interface-contract.md` 全量（Phase 3）
- 既有前端约定（组件库、状态管理、路由约定、目录结构）
- 不读：后端内部实现细节（表结构、服务划分）——那是 04 的领域

## Phase 2 · 契约诉求

站在前端角度提要求，**只提「我要什么」，不提「你怎么实现」**：

```markdown
### 接口：<用途>
- 场景：<哪个页面/交互触发>
- 方法 + 路径建议：GET /api/xxx
- 请求参数：<字段名 | 类型 | 必填 | 说明>
- 响应字段：<字段名 | 类型 | 说明 | 前端用途>
- 数据量级：<预估单次返回条数，决定要不要分页/虚拟滚动>
- 实时性：<轮询 / 一次性 / 需要推送>
- 错误码：<前端需要区分处理的错误场景>
- 性能要求：<首屏/交互可接受的 P95 耗时>
```

## Phase 3 · 前端设计内容

1. **页面/组件结构**：路由、页面、组件树、复用关系。**复用关系必须附路径**——写「复用 BaseTable」就要给出它在代码库中的位置；给不出路径标 `UNVERIFIED`，不得写进设计（写进去 = 给下游埋雷）。
2. **状态设计**：本地状态 / 全局状态 / 服务端状态，各自归属
3. **数据流**：接口调用时机、缓存策略、loading/empty/error 三态
4. **交互细节**：关键交互的状态机（如：草稿 → 提交中 → 成功/失败 → 重试）
5. **契约依赖**：明确列出依赖的接口，标注「若接口变更，影响第 X 节」
6. **兼容与降级**：老数据、权限不足、接口失败时的表现
7. **非功能**：性能预算、可访问性、埋点

## 判定标准

- [ ] 每个接口字段都标注了前端用途（用不上的字段要求后端删掉）
- [ ] 所有异常态（空/错/慢/无权限）都有设计
- [ ] 依赖的接口在契约中已存在且版本一致
- [ ] 复用既有组件/模式，无重复造轮子；**每条复用陈述附代码库路径**，无 `UNVERIFIED`

## 不做的事

- 不指定后端用什么技术、怎么存、怎么算。
- 不在设计里写实现代码（伪代码/状态机图可以）。
- **不私自改契约**——发现契约有问题，提交 `contract-change-request` 给 05。

## contract-change-request 格式

```markdown
## CCR · <task_id> · from 03
- 目标：interface-contract.md §<章节>
- 现状：<契约现在怎么写>
- 诉求：<希望改成什么>
- 原因：<前端哪块设计因此不成立>
- 影响面：<若改，前端设计的第 X 节需同步改>
```
