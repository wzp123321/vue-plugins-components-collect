# 完整跑通示例：课程表模板批量套用

用一次真实流程演示 6 个阶段怎么走，包含一次**契约冲突裁决**和一次**评审打回**。

## 需求原文（人输入）

> 「老师希望把上周的课表一键复制到本周，冲突的地方能提前标出来。」

---

## Phase 1 · 需求澄清（串行 2 轮）

**Round 1**

- `01 需求分析师` → `requirement-spec.md v1`
  - 场景：老师点「复制上周」→ 系统生成本周草稿 → 冲突项高亮 → 老师逐条处理 → 确认生效
  - 验收标准 AC-1..AC-5
  - open_questions：Q-1 冲突是「复制时检测」还是「生效时检测」？
- `02 需求挑战者` → `signal: REJECTED`
  - P0-1 **（可测性）** AC-3「冲突的地方能提前标出来」——「提前」是复制时还是保存时？两者实现完全不同
  - P0-2 **（完整性）** 未定义冲突类型。老师时间冲突、教室冲突、学生时间冲突是三件事
  - P1-1 **（边界）** 跨周/跨学期复制没说（上学期课表能不能复制到本学期）

**Round 2**

- `01` 修订 → v2：明确「复制即检测，生成草稿时标出」，定义三类冲突，限定「仅同校内相邻周」
- `02` → `signal: ACCEPTED`

**GATE-1** · 人确认需求冻结 ✅

---

## Phase 2 · 契约对齐（并行 → 汇聚）

并行发出：

- `03 前端架构师` 契约诉求：
  - 需要 `IF-1 复制预览`：入参 `sourceWeek, targetWeek`，响应要**带冲突详情数组**（类型/涉及课程/建议）
  - 数据量级：一周最多 60 节课
  - 性能要求：P95 < 1s（老师会等）
- `04 后端架构师` 契约草案：
  - 给 `IF-1`，但响应只有 `conflictCount`，详情需要再调 `IF-2 冲突详情`
  - **约束**：冲突检测要遍历教师/教室/学生三个维度的课表，单次计算 ~800ms；若详情内联，P95 会到 1.5s

`05 契约协调者` 比对：

| 项 | 前端诉求 | 后端草案 | 差异 | 裁决 |
|---|---|---|---|---|
| 冲突详情 | 内联在 IF-1 | 拆到 IF-2 | CONFLICT + COST | **内联** |
| 响应耗时 | P95 < 1s | 内联后 1.5s | CONFLICT | 放宽到 < 2s，前端加 loading |

裁决依据：
1. 需求 AC-1 要求「一键复制」——两次请求会破坏原子性，详情可能和预览不一致
2. 60 节课量级下，一次算完比两次请求的总耗时更低
3. 1s → 2s 的放宽：一周 60 节，老师在预览页停留时间远大于 2s，可接受

→ `interface-contract.md v1`，`status: LOCKED`

---

## Phase 3 · 详细设计（并行）

- `03` → `frontend-design.md v1`
  - 草稿态用本地状态，未确认不落库
  - 冲突项按类型分色：教师红 / 教室橙 / 学生蓝
  - 三态：loading（骨架屏）/ empty（无可复制课程）/ error（重试）
- `04` → `backend-design.md v1`
  - 新增 `t_schedule_draft` 存草稿
  - IF-1 不落库，纯计算返回；IF-3 确认生效才写 `t_lesson`
  - 三类冲突检测各自独立函数，便于单测

---

## Phase 4 · 设计评审（串行 2 轮）

**Round 1**

`06 设计评审官` → `signal: REJECTED`

- P0-1 **（可逆性）** `backend-design.md §6` 写「复制时先删除本周既有课程再插入」，**无回滚方案**。若中途失败，本周课表处于半删除状态
  - 要求：改为「先插入草稿 → 校验 → 单事务内 swap」，或用逻辑删除 + 版本号
- P0-2 **（契约一致）** `frontend-design.md §5` 引用了 `IF-2 冲突详情`，但契约 v1 已把详情内联进 IF-1，IF-2 已删除
  - 要求：删除该调用，改从 IF-1 响应读取
- P1-1 **（异常完备）** 未定义「本周已有生效课程时再复制」的覆盖策略

**Round 2**

- `04` 改设计：单事务 swap + `draft_id` 版本号，失败自动回滚
- `03` 删掉 IF-2 调用
- `06` → `signal: APPROVED_WITH_CHANGES`（P1-1 进开发 todo）

**GATE-2** · 人确认设计可执行 ✅

---

## Phase 5 · 开发（并行）

- `07 前端开发`：只拿 `frontend-design.md` + 契约 v1
- `07 后端开发`：只拿 `backend-design.md` + 契约 v1

开发中，前端发现：`conflict[].suggest` 字段后端返回的是课程 ID 列表，但设计里写的是「建议时间段文案」。

→ 提交 **CCR**：
```
目标：interface-contract.md §2 IF-1 响应字段 suggest
现状：类型 array<string>，未定义元素含义
诉求：明确为 array<{lessonId, targetSlot, reason}>
原因：前端 §6 冲突项渲染需要三个字段，当前只有 ID 无法出文案
影响面：前端 §6 无需改；后端 §3 IF-1 需调整返回结构
```

`05` 裁决：APPROVED → 契约 v2，通知后端改 §3，前端不改。

**GATE-3** · lint / type-check / 单测 / build 全绿 ✅

---

## Phase 6 · 验收自测（分层）

`08a` 契约层 + `08b` UI 层分别验 AC-1..AC-5：

| # | L1 契约层 | L2 UI 层 |
|---|---|---|
| AC-1 一键复制生成草稿 | PASS | PASS |
| AC-2 冲突项高亮 | PASS | PASS |
| AC-3 三类冲突分别标识 | PASS | PASS |
| AC-4 确认后生效 | PASS | PASS |
| AC-5 中途失败可回滚 | PASS | **FAIL** — BLOCKER |

**D-1 [BLOCKER]**：复制过程中强制刷新页面，`t_lesson` 残留部分新数据且无 `draft_id` 可追溯
- 对应 AC-5
- 期望：要么完整生效，要么完整回滚
- 实际：出现中间态
- 根因分层：**设计** —— 后端设计 §3 按「先删后插」写了两条独立事务，没定义刷新中断时的中间态处理；代码只是忠实实现了这个有漏洞的设计
- 回溯目标：**Phase 3**（04 补事务边界 + draft 先行落库），不是 Phase 5

> 若按旧做法无脑打回 Phase 5，07 只能在既有设计框架内修修补补（比如给删插包 try-catch），中间态问题还会以别的形式复现。

**修复后 Round 2**（04 改设计为单事务 + draft 先行落库，07 按新设计重实现）→ 两层全 PASS → **GATE-4** 人确认交付 ✅

---

## 本次流程的关键收益

| 环节 | 若没有流程会怎样 | 有了流程 |
|---|---|---|
| 需求「提前标出」 | 开发到一半才发现歧义，返工 | Phase 1 挑战者当场问清 |
| 冲突详情内联还是拆分 | 前后端各写各的，联调时对不上 | Phase 2 契约对齐，一次裁决 |
| 「先删后插」无回滚 | 上线后出脏数据 | Phase 4 评审 P0 拦下 |
| `suggest` 字段语义不明 | 前端写死猜测，后端一改就崩 | CCR 流程，改契约 + 通知双方 |
| 刷新导致中间态 | 线上事故 | Phase 6 验收 BLOCKER 拦下 |
