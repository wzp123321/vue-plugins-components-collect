# 设计评审评分标准（Rubric）

06 评审官按 8 个维度打分，每维 1-5 分。

## 评分锚点

| 维度 | 1 分（不可接受） | 3 分（可接受） | 5 分（优秀） |
|---|---|---|---|
| **需求覆盖** | 有验收标准完全无设计 | 主要标准覆盖，边角缺失 | 逐条对应，异常场景也覆盖 |
| **契约一致** | 引用契约中不存在的接口 | 接口存在，个别字段对不上 | 版本一致、字段用途明确、无冗余 |
| **异常完备** | 只设计成功路径 | 覆盖了常见失败 | 失败/空/超时/并发/权限/边界全覆盖 |
| **既有约定** | 违背项目既有规范或重复造轮子 | 基本符合 | 充分复用既有组件/模式，并说明复用点 |
| **可落地** | 关键逻辑写「待定」，无法开工 | 主体明确，细节需开发自行判断 | 粒度足够直接编码，无歧义 |
| **非功能** | 完全没提性能/安全/可观测 | 提了但无量化 | 有量化指标 + 监控点 + 兜底 |
| **可测性** | 无法据此写验收用例 | 主要路径可测 | 每条验收标准都能映射到具体验证方法 |
| **可逆性** | 不可逆改动且无回滚方案 | 有回滚但没验证过 | 有灰度 + 回滚 + 老数据兼容方案 |

## P0 判定（任一命中 → REJECTED）

1. 某条**验收标准完全无设计覆盖**
2. 设计引用了**契约中不存在的接口/字段**
3. 前后端对同一接口理解不一致（契约未 LOCKED 就各写各的）
4. 存在**不可逆**改动且无回滚/灰度方案
5. 设计粒度**不足以开工**（关键逻辑「待定」）
6. 违背**安全/权限**硬性规范

## P1 判定（不阻塞，进开发 todo）

- 异常路径覆盖不全
- 非功能指标未量化
- 未复用既有组件
- 可测性差但主要路径可验
- 文档内部前后不一致

## 不算问题（避免评审噪音）

- 命名风格、代码组织偏好
- 「有更优方案」但现方案不会导致返工或事故
- 需求该不该做（那是 GATE-1 的事）
- 主观「不够优雅」

## 评审纪律

- **位置必须具体**：写「§3 IF-2」，不写「后端设计里有问题」
- **要求必须可执行**：写「补充失败补偿方案」，不写「考虑一下异常」
- **理由必须关联后果**：写清「会导致 X 场景脏数据」，不写「我觉得不好」
- 发现契约问题 → 不直接判 P0，转 05 走 CCR
