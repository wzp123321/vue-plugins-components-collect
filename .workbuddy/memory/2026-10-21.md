### 2026-10-21 更正：整体变暗的根因是 mixPass 缺 sRGB 输出转换（推翻了上一条的 include 位置）
- 用户实跑反馈「整体颜色暗了好多」。灯光 ×π 补偿是对的，问题不在灯。
- **真根因**：项目走 `EffectComposer`（RenderPass → mixPass），整条链的 renderTarget 都是 `LinearSRGBColorSpace`，最后一道 `bloomMixShader`（`useMapViewport.ts:78`）**直接 renderToScreen 写 canvas 却只做了 `gl_FragColor = vec4(base.rgb + bloom, base.a)`，没有 linear→sRGB 转换**。ShaderMaterial 不像内置材质会自动补 `colorspace_fragment`，于是全画面按线性值直接显示 → 整体压暗。
- **修正**：`#include <colorspace_fragment>` 加在 `bloomMixShader` 的 fragmentShader 末尾（只转 rgb，alpha 必须原样带出，否则大屏底图透不上来）。之前加在 `drawRegion` / `spotLayer` / groundMat 上的三处**全部撤掉**——它们渲染到线性 renderTarget，此时 three 的 `linearToOutputTexel` 目标色空间被强制为 LinearSRGB（`WebGLPrograms.getParameters()` 里 `currentRenderTarget !== null` 分支），include 是 no-op，留着只会误导。
- **通用规则（背下来）**：接 composer 的场景里，`colorspace_fragment` 只加在**最后一道 renderToScreen 的 ShaderPass** 上；场景内材质一律不加。不走 composer（直接 `renderer.render`）时，内置材质自动转，自定义 ShaderMaterial 才需要自己加。
- 副作用预期：加法混合（bloom、AdditiveBlending）现在发生在线性空间，比旧的 sRGB 空间相加略亮，属物理正确行为；若觉得泛光过头调 `UnrealBloomPass` 的 strength（当前 0.62）。

### 2026-10-21 最终结论：整体退回旧颜色管线（上面两条都被这条取代）
- 用户续报「边境线偏粗、省份背景偏暗」。查实根因：**three ≤0.147 的链路本就跳过了 gamma 解码** —— `ColorManagement` 默认关闭，Color 存 sRGB 数值，配合默认线性输出，等价于「不解码直接算、不编码直接显示」，所以同样的配置值看起来更亮。0.173 走物理正确流程后必然暗一截。边境线显粗是连带效应（暗底上的亮线对比更强），不是线宽数值变了。
- 顺带查清 Line2 线宽：r147 的 `LineSegments2` **没有 `onBeforeRender`**，resolution 完全靠项目手动 `setLineResolution`（CSS 尺寸）；r173 新增了 `onBeforeRender`，每帧用 `renderer.getViewport()`（同样是 CSS 尺寸，**不乘 pixelRatio**）覆盖。两边都是 CSS 尺寸，**线宽并没有变**，不要往线宽上改。
- 最终改法（新增 `src/three-compat.ts`，main.ts 首行 `import './three-compat'`）：
  1. `THREE.ColorManagement.enabled = false` —— 必须独立成模块并在 main.ts 第一行导入。ESM 按 import 顺序求值，页面是路由懒加载所以排在后面，模块顶层的 `new THREE.Color(...)`（如 `data.ts` 的 `DEEP_COLOR`、`drawFlyLine` 的 `TRACK_NEAR`）也能被正确覆盖。
  2. `renderer.outputColorSpace = THREE.LinearSRGBColorSpace` —— 两处：`useMapViewport.ts`（地图）与 `useThreeScene.ts`（5 个 demo 共用）。不设的话输出仍编码一次、整体发亮。
  3. 撤掉 mixPass 的 `#include <colorspace_fragment>`（旧管线下是死代码），留注释说明将来切回正确管线时才加、且只加在最后一道。
  4. **灯光 ×π 的 `legacyIntensity` 保留** —— 它修的是 r160 删除 `useLegacyLights` 这个独立问题，与颜色管线无关，两者叠加才等于 0.147 的原始观感。
- **教训**：three 跨大版本升级时，「颜色看起来不对」优先怀疑颜色管线开关（ColorManagement + outputColorSpace），别从具体材质/线宽/光照数值上找。方案 B（保留新管线靠调色还原）在离线环境下不可行 —— 要逐通道反推 sRGB→线性→sRGB，必须反复实测，远不如直接关开关一次到位。

### 2026-10-21 hover 抬升改成「拉高板块」而非「整体上移」
- 用户反馈「鼠标悬浮时省份像偏移，不像抬升」。原实现 `gsap.to(node.object.position, { z: LIFT_HOVER })` 是把整块板 position.z 上移 —— 板块底边跟着离开地面，斜俯视透视下被读成整块平移。
- 改法：`gsap.to(node.object.scale, { z: 1 + lift / mapConfig.depth })`。`ExtrudeGeometry` 的 z 从 0 到 depth（原点在底面），放大 z 只推高顶面、底面纹丝不动，底边留在原地形成参照，才有"从地里抬起来"的感觉。线框与顶面同在一个 object，按同比例上移不会脱开。
- 关键不变量：`MAP_EXTENT = 130`（地图归一化边长）、`depth = 6`、`LIFT_HOVER = 1.8`（+30%）、`LIFT_FOCUS = 0.9`。lift 除以 depth 再 +1 得到缩放系数。
- 已知副作用：侧壁共享 ShaderMaterial 里用 `vZ / depth` 归一化渐变，拉高后超过 depth 的部分会 clamp 在 1.0，hover 那 0.22s 内几乎看不出；要彻底干净需给侧壁传 per-object 的 lift，不值得。`useMapLayer.clear()` 里的 `killTweensOf` 已同步改成 `node.object.scale`。

### 2026-10-21 飞线锯齿：antialias 在 EffectComposer 下失效
- 用户问"缩放到 1.x 后飞线还有锯齿，好优化吗"。根因很明确：`new WebGLRenderer({ antialias: true })` **只对直接渲染到默认帧缓冲生效**；一旦接 `EffectComposer`，画面先进 renderTarget，而 `WebGLRenderTarget` 的 `samples` 默认是 **0**（无多重采样），antialias 完全没用上。飞线是细长高对比几何（`MeshBasicMaterial` 三角带，无 discard/smoothstep 软边），锯齿最明显。
- 改法：`useMapViewport.ts` 主 composer 改用显式带 MSAA 的 target ——
  ```ts
  const composerTarget = new THREE.WebGLRenderTarget(width, height, { type: THREE.HalfFloatType, samples: 4 })
  composer = new EffectComposer(renderer, composerTarget)
  ```
- 已核实 samples 不会丢：`RenderTarget.copy()`（`src/core/RenderTarget.js:166`）有 `this.samples = source.samples`，`EffectComposer` 构造时 `renderTarget2 = renderTarget.clone()`，`setSize` 也是 clone 后设尺寸，三处都保留。
- `bloomComposer` **不用开** MSAA：它的内容马上进 `UnrealBloomPass` 高斯模糊，锯齿会被抹平，开了纯浪费带宽。
- 若 4x 还不够，下一档按性价比排序：① `setPixelRatio(Math.min(dpr, 1.8))` → 2（+23% 像素）；② 在 mixPass 后追加 `SMAAPass`（能处理 MSAA 覆盖不到的亚像素细节，但要额外 pass + 纹理）。

### 2026-10-21 实测性能并做 draw call 合并（1374 → 预期 200~300）
- 性能面板实测：**33 FPS / 1374 calls / 353k tris**。我上一轮估 200 calls 完全错了。
- **真因**：`china.json` 是 35 个 feature → **339 个 polygon / 339 个 ring**（海南省独占 133 个环＝南海诸岛，浙江 44、广东 23、福建 17），而 `createRegion` / `createOutline` 都是**按 ring 建对象**：每环 1 个 MeshPhongMaterial + 1 个 Mesh（`[顶面,侧壁]` 双材质 = 2 draw call）+ 1 条 Line2 = 3 次。339×3≈1017，加柱子/飞线/后处理正好 1374。1374 × 约 20μs ≈ 27ms/帧 ≈ 37 FPS，与实测 33 吻合 —— **瓶颈是 CPU 提交 draw call，不是 GPU 填充率**。
- **改法（每省合并）**：
  - `drawRegion.ts`：一个省的**所有 ring 的 Shape 合成一个数组**，一次性 `new THREE.ExtrudeGeometry(shapes, ...)`；一个省只建**一个** MeshPhongMaterial；边界线从「每环一条 Line2」改成**一个 `LineSegments2`**（闭合环拆成相邻点对 `[ax,ay,az,bx,by,bz]`，末点接回首点，全塞进一个 `LineSegmentsGeometry`）。
  - `drawOutline.ts`：同样合并，且实线与光晕**共用同一个 geometry**，整层只剩 2 次 draw call。
- 保持不变的不变量：`mesh.userData.region = object`（拾取）、`object.scale.z` 抬升（hover 拉高）、`topMaterials` 数组（现在长度恒为 1，`paint()` 里的 `for...of` 无需改动）、`setLineResolution` 同步的三个材质（LineMaterial 与 LineSegments2 通用）。
- 合规注意：海南 133 个环（南海诸岛）**不能按面积过滤删掉**，合并时照样全量写入顶点。
- 待验证：合并后视觉应与之前一致；若出现顶面缺失或界线错乱，优先查 shape 数组与线段对的闭合逻辑。

### 2026-10-21 修正：合并 geometry ≠ 合并 draw call（ExtrudeGeometry 按 shape 分组）
- 上一次合并后实测只从 1374 降到 **1079**（35 FPS），远低于预期。原因查清：
- **`ExtrudeGeometry` 对每个 shape 各 `addGroup` 两次** —— `buildLidFaces()` 里 `addGroup(..., 0)`、`buildSideFaces()` 里 `addGroup(..., 1)`，而这两个函数定义在 `addShape(shape)` 内部，逐 shape 调用（`src/geometries/ExtrudeGeometry.js:553 / :577`）。所以 339 个 shape → **678 个材质组**。
- **Mesh 配材质数组时，draw call 数取决于 `geometry.groups.length`，不是 Mesh 数量、也不是材质数量。** 合并成一个 geometry 后仍是 678 次 —— 白合。那 295 的下降全部来自内部界线（339 条 Line2 → 35 个 LineSegments2）和外轮廓。
- 修复：`drawRegion.ts` 新增 `collapseExtrudeGroups(geometry)` —— 按 `materialIndex` 把索引缓冲重排成两段连续区间（同整型宽度，`index.array.constructor` 取），`clearGroups()` 后重建为 2 组。顶点数据不动，视觉零变化。
- **通用结论（记住）**：three 里判断 draw call 别只看对象数，要数 `geometry.groups.length`；用 `mergeGeometries` 之类合并时，各组也会保留。
- 剩余待查：折叠后预计 1079-676 ≈ 400，若仍偏高，大头在飞线 / 数据柱 / 轨道环（每条飞线的 track+streak 是独立 Mesh，blast 层对象还要在 bloom 趟再画一遍）。

### 2026-10-21 再修正：ExtrudeGeometry 是非索引几何，必须先补索引
- 折叠写完实测数字**一点没变**（1079 / 372k 原样）。用 node 直接跑 three 验证（`node --input-type=module -e "import * as THREE from './node_modules/three/build/three.module.js'"`，注意必须指向 build 产物，直接 `import 'three'` 在 node 里探索 exports 会失败）：
  - `new ExtrudeGeometry([3 个 shape], ...)` → **`geometry.index === null`**（非索引，三角形汤），`groups.length === 6`（每 shape 两组）。
  - 我上一版的 `if (!index) return` 正好命中非索引分支 → 整段代码一行没执行。
- 最终修法：`collapseExtrudeGroups` 先补一份 `0..N-1` 的 `Uint32Array` 索引（顶点不共享，补索引不省顶点，只为让分组可重排；五万顶点约 200KB），再按 materialIndex 把索引重排成两段连续区间、`clearGroups()` 重建 2 组。非索引几何的 `group.start` 指顶点序号，与补出的 0..N-1 索引一一对应。
- **node 侧验证配方（值得复用）**：把逻辑抄进 `--input-type=module -e` 脚本，用 133 个 shape 跑一遍 —— 结果 `groups 266 → 2`，`索引总数 4788 === 顶点数`，两组之和等于索引总数（覆盖完整），索引值未越界。
- 教训：改 three 几何的 group/index 之前，**先在 node 里把真实数据结构打出来**（`index`、`groups`、`attributes.position.count`），比读源码猜测快得多，也不依赖浏览器。

### 2026-10-21 性能收尾：draw call 降完，瓶颈转到 GPU
- 组折叠后实测 **35 FPS / 469 calls / 372k tris**（calls 从 1374 → 469，降了 905）。但 FPS 只 30→35，说明 CPU 侧已不是瓶颈（469×约 20μs ≈ 9.4ms，而 35FPS = 28.6ms/帧）。
- 剩余 469 的构成估算：顶面 70（35 省 × 2 材质）、内线 35、外轮廓 2、飞线约 150（track+streak+涟漪，bloom 趟还要再画一遍）、数据柱约 140、星空/地面/后处理 pass 约 70。
- **飞线与数据柱不建议合并**：它们的顶点每帧都在动，合成大 buffer 等于每帧上传整块数据，风险大收益小。
- 最终把 MSAA `samples: 4 → 2`（`useMapViewport.ts` 的 composerTarget），预期 42~48 FPS。注释里写明取舍与改回方式。
- 未动：`pixelRatio` 仍是 `Math.min(dpr, 1.8)` —— 降到 1.5 能上 55+ 但整体变软，展示页不值得。
- 用户表示"先这样"，本轮收工。
