# SDD 多智能体协同开发编排器

## 0. 定位与铁律

本 skill 是**编排层**，不是实现层。它把「需求入口 → 设计 → 并行编码 → 评审 → 自测 → 提交」这条链跑起来，实际工作全部交给子智能体完成。

### 五条铁律（违反一条编排就失效）

| # | 铁律 | 理由 |
|---|---|---|
| 1 | **编排者不读代码、不写代码、不跑测试** | 只做分档、派活、收产物、判卡点。编排者一旦开始读文件，context 会被文件读操作和 diff 塞满，丧失对全局流程的掌控力（Roo Code Orchestrator 明确禁止 orchestrator 读写文件，原因就是防 context poisoning） |
| 2 | **子任务一律 fresh context** | 每个子智能体独立上下文，向下只给初始指令，向上只回收 summary（≤30 行） |
| 3 | **产物在磁盘，不在对话里** | 规格、设计、任务、评审结果全部落文件，靠路径交接。子智能体看不到主对话，这是唯一可靠的交接方式 |
| 4 | **卡点必须人工确认** | 不得代替用户拍板，不得越过卡点，不得因为「看起来没问题」就自行放行 |
| 5 | **不确定就标「待确认」并问人** | 版本号、业务口径、需求边界——绝不编造 |

### 通用性要求

本 skill 可复制到任意项目使用。**不得硬编码任何具体项目的路径、技术栈或 skill 名**，项目差异一律靠 §2 的运行时发现机制解决。

## 1. 入口：需求来源解析

用户给出以下任一形式即接管流程：

| 入口类型 | 解析动作 |
|---|---|
| **本地需求文档路径** | 直接读取。读到密文或二进制时，改用该项目内可用的明文读取手段（如 `git show HEAD:<path>`），并在现状摘要中注明 |
| **git issue 编号/URL** | 先 `git remote -v` 判断平台；GitHub 用 `gh issue view <n>`，GitLab 用 `glab issue view <n>`；CLI 不可用则请用户直接粘贴 issue 正文，不要卡住 |
| **用户口述** | 先落盘成需求文档再继续，绝不让对话历史承载需求 |

解析完成后向用户复述一句需求摘要，确认理解无误再进分档。

**加密环境文件读取兜底（重要）**：若项目所在机器有透明加密（如 E-SafeNet 亿赛通），`.java` / `.md` 等可能被加密为二进制，Read 会拿到密文并误报 "Cannot display content of binary file"。读取任何源码 / 文档文件**前**，先用 `head -c 64 <file>` 探一下是否密文（出现 `E-SafeNet` 标记或大量 `\0` 即密文）；密文改用 `git show HEAD:<path> > /tmp/plain.txt` 取明文，**不要**用 cat / Read 直接读。子智能体派活时也须在「边界 / 约束」里写明此兜底，避免 agent 读加密文件卡死、谎报"不可读"。

## 2. 项目锚点发现（所有流程的第一步）

在开始任何阶段前，先摸清「这是哪个项目、它有哪些规矩」。按序扫描，取第一个存在者：

### 2.1 项目规约（constitution）

```
.sdd/constitution.md  >  AGENTS.md  >  CLAUDE.md  >  项目 README
```

### 2.2 可用能力（skill 清单）

```
{workspace}/.workbuddy/skills/    用户级与项目级自定义 skill
{workspace}/ai-knowledge/skill/   本仓库内置 skill（energy-vpp-service 的用法）
~/.workbuddy/skills/              用户级全局 skill
```

**只记录名字与职责，不读全文。** 分类登记为：后端规范 / 前端流程 / 文档规范 / 契约同步 / 提交规范 / 编码规范 / 测试规范。

### 2.3 项目记忆

```
.workbuddy/memory/MEMORY.md        长期项目约定
.workbuddy/memory/YYYY-MM-DD.md    最近 3 天的日志
```

跨项目同类经验用 `conversation_search` 检索。

### 2.4 文档产物路径

优先沿用项目规约中已声明的目录；未声明时按已确认的默认值：

```
doc-repo/prd/{版本}/          需求规格 spec、澄清记录
doc-repo/design/{版本}/       设计文档（目录/文件名/章节骨架以项目指定的文档规范 skill 为唯一真源）
```

### 2.5 版本号

产物目录含版本号，**版本号不得编造**：入口文档自带则提取并报确认；没有则用 AskUserQuestion 问一次，问到后全程复用。

## 3. Stage 0：上下文装载（所有档位必做，且最先做）

### 3.1 先问后读（硬顺序，不可倒置）

进入任何代码检索**之前**，先用一轮 AskUserQuestion 把两件事问掉：

1. **参考代码指认**：「这个需求有没有可以参考的既有功能 / 模块？有就给个路径或模块名」
   - 用户指认 → 只定向读指认路径及其直接依赖，**不跑全库相似性检索**
   - 用户说没有 / 不确定 → 才做相似模块检索，且只列路径 + 一句话职责，**不深读实现**
2. **档位预判**：一句话问「这个改动大概什么量级」，与 §4 分档规则对表

用户回答之前**禁止扫描代码库**。代码阅读是 Stage 0 最贵的动作，能省则省；用户指认的参考路径要记入 state.json，后续派活直接复用。

### 3.2 现状摘要（≤30 行，超了就砍）

产出一份 **≤30 行的现状摘要**，给用户确认后才进入下一阶段。摘要必须包含：

1. 需求一句话概括
2. 档位建议与理由
3. 本项目可用 skill 清单（只列名字与职责）
4. 相似模块清单（用户指认的优先并标注；检索得来的注明「自动检索」）
5. 检索到的历史踩坑记录（conversation_search，仅与本次需求相关的）
6. 需要用户确认的未知项（与 §3.1 的回答合并去重后**一次**列出）

## 4. 分档路由

| 档 | 判定标准 | 跳过的门 | 必走阶段 |
|---|---|---|---|
| **轻档** | 单模块、不新增接口/表/字段、改动点 ≤3 处 | 卡点①（spec 评审门）、卡点②（前端设计门） | Stage0 → 实现 → 交叉评审 → 卡点④提交门 |
| **中档** | 新增接口但不跨端；或不新增表 | 卡点②（前端设计门） | Stage0 → spec → 后端设计 → 任务 → 实现 → 验收 → 自测 → 卡点④ |
| **重档** | 跨前后端 / 多模块并行 / 新增表或 DDL | 无 | 全链路 |

- 分档结论必须报给用户，一句话即可改档
- **分档是路由不是免死金牌**：过程中发现实际超出档位范围，立即升档并告知用户

## 5. 阶段链

### Stage 1：需求澄清与规格

- 用 AskUserQuestion 把所有模糊点**一次问清**，不要分批挤牙膏
- 问题与答复落盘 `questions.md`（**问题账本**，全流程唯一事实源）：
  - 每个问题编号 Q1、Q2…，**一个问题只允许问一次**；后续任何阶段（含卡点确认）想再问，先查账本，已闭环的直接引用结论，不重问
  - 子智能体**一律不得直接问用户**：有疑问写进返回格式的「待确认项」，由编排者查账去重后**合并成一轮**批量问
  - 重复问已闭环的问题视同编排失误
- 产出 spec 到 `doc-repo/prd/{版本}/`
- **卡点① spec 评审门**（轻档跳过）：用户确认后才进设计

### Stage 2：设计（后端先行，前端跟随）

1. **后端设计**：调能力发现阶段登记到的**文档规范类 skill**，产出设计文档。文档规范以该项目指定的规范 skill 为唯一真源，编排层不自带格式。
   **产物按需裁剪**：确认不涉及任何表结构变更（无新表 / 无改字段 / 无 DDL）时，**不产出数据库设计文档**——在主设计文档的「表结构设计」小节写明「本次无表结构变更」及理由即可；涉及表变更才建库档。编排层裁剪的是「产出哪些文件」，文档内部格式仍归规范 skill 管
2. **DDL 单独确认**：不得与设计文档打包一起通过
3. **契约冻结**：调**契约同步类 skill** 的「变更预告」模式，把接口出入参先给到前端
4. **前端设计**：按后端出入参调整设计，走前端流程类 skill
5. **卡点② 设计评审门**（轻档、中档跳过）：用户确认后才进拆解

### Stage 3：任务拆解与波次排程

- 前后端各自拆 `tasks.md` + `checklist.md`，粒度 = 最小可验证改动
- 标出模块间依赖，排出**波次**：
  - 先分前后端两条线
  - 各自内部：无依赖关系的模块同波并行；有依赖关系的严格按序
  - 跨端：后端接口契约先冻结，前端才能进实现波
- 波次表报给用户确认

### Stage 4：波次并行实现

- **契约冻结门（进并行前必过）**：`questions.md` 中所有问题必须**闭环**，或每项带**显式 default 决策**（标注「用户未决，按默认 X 推进」）。**禁止带着未决的开放问题进并行波次**——否则各波基于不同假设各自实现，事后返工会抵消并行收益（实测：收入口径 course.price vs student.price 歧义、save-month 语义未决时并行，波次间已分叉）。未闭环项必须先经一轮 AskUserQuestion 批量确认，再派并行波。
- **编排者抽查门（信任但验证）**：每波回报"通过"后，编排者必须用 **Grep 精确抽查 1–2 个关键端点 / 路径是否真在文件里**（只 Grep 不深读实现，不违反铁律①），确认存在且非占位，再放行下一波。子代理 summary 的"通过"不可直接采信。
- **并行是硬要求，不是愿望**：同波内无依赖的子任务必须在**同一条消息里同时派出**（并发发起多个子智能体），禁止「派一个、等完成、再派下一个」的串行伪并行；只有存在数据 / 契约依赖的任务才允许先后
- **让用户看得见并行**：每波开始前播报并行结构，如「Wave 1 并行 3 路：后端契约 / 前端列表 hook / 前端导出 UI」；每路完成更新一行状态（例：`[Wave 1/2] 后端 ✓ | hook ✓ | UI · 进行中`）。若某波实际只有一路，要明说「本波 1 路串行，因存在依赖」，不许含糊带过
- 同波内每模块一个子智能体，**fresh context**，只给它自己的 slice
- **卡点③ 逐模块验收门**（轻档跳过）：**换另一个子智能体**做交叉 review（自己 review 自己没有意义），不通过则返工，**返工 ≤2 轮，第 3 轮强制人工介入**

### Stage 5：集成 · 自测 · 收尾

1. **集成审计（强制派专门子代理，禁止编排层口嗨联调）**：派一个**只读**子代理做「后端路由 × 前端 api 调用 × 契约(BE-API/接口表)」三方静态比对，输出对齐矩阵 + 阻断清单（端点缺失 / 路径错配 / 入参错配 / 孤儿端点 / **字段类型错配**）。**0 阻断才放行**，否则回到对应波次返工。编排者按铁律①不读代码，靠各波自报的"联调"会漏掉端点缺失、空壳、路径漂移、字段类型错配这类跨模块问题——实测某重档项目 Wave C/E 评审均"通过"，但 5 个核心端点后端根本没写出来，靠专门审计才抓出；另有"路径对但类型错"的隐性 bug（前端发 boolean、后端收 Integer，Jackson 反序列化运行时才炸），靠此闸门在交付前拦截。

   **字段类型契约核对（必做子项）**：审计除路径/端点外，必须**逐字段比对** 前端 `types/index.ts` + `api/*.ts` 的**发参/收参 JSON 标量类型** 与 后端 DTO / 实体 的 Java 字段类型。凡出现 `Boolean↔Integer`、`number↔String`、`String↔number` 等 JSON 标量不匹配，或 必填/null 语义冲突，一律记 🔴 阻断。重点核查 TINYINT(1/0) 开关量、金额、日期等易分叉字段；发现系统性分叉写入 `.sdd/known-patterns.md`（KP 类）供跨波回归。
2. **跨波回归**：把各波评审发现的系统性 pattern（如「路径偏离契约」「javax 命名空间未迁 jakarta」）汇总进 `.sdd/known-patterns.md`，集成审计与返工时强制全波扫描同类问题，避免同 bug 在相邻波重复出现。
3. **真实构建门（硬门）**：强制真实执行 `mvn compile` / `npm run build` / typecheck，并以**退出码为准**，**不得仅凭子代理 summary 判定"通过"**。环境无 JDK / Maven / Node 时，编排者必须把它标记为 **blocking handoff**——写进 `state.pending_confirmations` + 向用户明确"本环境无法编译，需你本地验证"，**不得静默跳过说"通过"**。
4. **自测**：需求条目 → 设计章节 → 任务 → 单测，**四列追溯矩阵**，缺哪条一眼可见
5. **文档同步（spec↔code 一致性前移）**：每个卡点③/④ 带一条"契约 vs 实现"漂移检查，漂移**当时就回写**文档（以代码现状为准），不积压到收尾。Stage 5 收尾再做一次整体同步。
6. **记忆回写**：把本次技术决策与踩坑（含 known-patterns 新增项）写进项目日志
7. **卡点④ 提交门**

## 6. 卡点协议

| 卡点 | 时机 | 确认内容 | 跳过条件 |
|---|---|---|---|
| ① | spec 完成后 | 需求范围、边界、验收标准 | 轻档跳过 |
| ② | 设计完成后 | 后端设计产物（按需含库档，无表变更则无库档）+ DDL（如有）+ 前端设计 | 轻档、中档跳过 |
| ③ | 每模块完成后 | 交叉评审结论、返工 | 轻档跳过 |
| ④ | 全部完成后 | 变更清单、commit 拆分方式、是否 push/开 MR | **永不跳过** |

**用户已选定最保守策略**：commit 之前也必须看 diff。因此卡点④的执行顺序是：

1. 编排层汇总本次全部改动，产出**变更清单**（文件 → 改了什么 → 对应哪个任务）
2. 用 AskUserQuestion 让用户选：全部提交 / 拆成几次提交 / 指出要改的地方
3. 用户确认后才按项目的提交规范 skill 执行 commit
4. **push、开 MR / PR 一律单独再确认一次**，不得与上一步合并成一次询问

## 7. 子智能体派活契约

每个子任务的派活 prompt 必须包含这七段，缺一段就别派：

```
角色       ：一句话，如「后端 CmdExe 实现者」
目标       ：这个模块要交付什么，必须可验证
输入产物   ：绝对路径 + 精确锚点（文件 → 章节号 / 方法名 / 关键片段），可附 ≤20 行结论性摘录
输出产物   ：要写哪些文件，绝对路径
约束       ：指向规范 skill 与规约文件的路径；可附 ≤20 行关键约束摘录（以原文件为准，不整段搬运）
边界       ：禁止改哪些文件；禁止越权改前端或后端代码；**禁止在输入清单之外漫游读代码**
返回格式   ：summary ≤30 行 —— 改了哪些文件、为什么这么改、怎么验证的、还剩什么没做、**待确认项**
```

红线：不要把整个对话历史塞给子智能体；不要让它自己去猜规范在哪；不要让它顺手做职责外的改动。

**评审类子任务（卡点③）的强制检查项**：交叉 review 不只看"我这块对不对"，必须额外核对三条，缺一条结论无效：
- ① **存在性**：声称交付的接口 / `@Mapping` / 导出函数是否**真在对应文件里**（Grep 确认），防止"评审通过但端点根本没写"。
- ② **非占位**：方法体 / 组件是否为**非空真实逻辑**（不是 `return null` / 空 list / `TODO` / 写死常量 / 只有模板骨架没接数据），防止空壳漏过。
- ③ **契约吻合**：路径、method、入参名/类型是否与契约(BE-API/接口表)精确一致；偏离即记 🔴/🟡。

**子代理派发健壮性**：派活前**校验参数 JSON 合法性**（避免 malformed JSON 导致 agent 创建失败需手动重派）；对 `429` 限流 / 创建失败**自动重试 1–2 次**并退避，不报错中断整波；限流期间可串行降级，不要整体失败。

**派活质量直接决定编码速度**：锚点越准，子智能体探索越少。缺上下文时子智能体应在「待确认项」里报「缺什么」，由编排者补进输入清单再派——而不是它自己全库漫游。用户在 Stage 0 指认的参考模块，其文件清单必须原样进入每个相关子任务的输入产物，这是「先问后读」在编码阶段的延续。

## 8. 断点续跑

在 `.sdd/state.json` 维护状态：

```json
{
  "requirement_source": "issue #123 或 文档路径",
  "tier": "轻|中|重",
  "version": "v4.5.0",
  "current_stage": "Stage 3",
  "completed_modules": ["后端-站点管理", "后端-交易单元"],
  "artifacts": { "spec": "doc-repo/prd/v4.5.0/spec.md" },
  "pending_confirmations": ["版本号"]
}
```

每次进入卡点前落盘一次。会话中断后重新触发时，先读 state.json 从断点恢复，不重跑已完成阶段。

### 8.1 跨波回归载体 `.sdd/known-patterns.md`

格式（首次发现系统性问题时即创建，不预建空文件）：

```
# known-patterns（跨波回归共享，编排层与各波强制参考）
| 编号 | 类别 | 现象 | 根因 | 波及波次 | 处理方式 |
```

## 9. 红线清单

- 编排者本人不改代码、不跑测试、不直接提交
- 版本号、业务口径不确定 → 标「待确认」并问人，**绝不编造**
- 不得越过任何卡点；轻档跳过的门仅限 §4 明确列出的
- 未经用户确认不得改前端代码（契约同步类 skill 的红线）
- 不得把多个模块的改动混进一次提交，除非用户明确要求
- 破坏性操作（批量删除、覆盖、发布、改线上）先列清单说清后果再等确认

**效率红线（用户实测反馈固化，同等强制力）：**

- 同一个问题不允许问第二次——以 `questions.md` 为准，已闭环直接引用结论
- 任何阶段向用户的中间汇报 **≤15 行**；长分析一律落盘为文件，对话里只留结论 + 路径
- Stage 0 必须先问「有无参考功能」再动代码；用户指认后禁止全库相似性检索
- 同波无依赖子任务必须并发派出；串行伪并行视同该波未按规范执行
- 无表结构变更不得产出数据库设计文档
- 编码子智能体的探索范围 = 派活契约的输入清单；清单外需要更多上下文，回报「待确认项」而不是自己漫游
